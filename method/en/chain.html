RULE CHAIN

The 12-rule chain

Every rule states an id, a criterion and a challenge point. The criterion must resolve to a formula or a threshold; the challenge point must name a disputable input or constant, not an attitude.

Criterion = executable formula / threshold Challenge point = an assumption a counter-example can overturn
MTH-01Decision threshold

Cost-asymmetry threshold

Cost-asymmetric threshold

The relative cost of the two error types sets the interception probability; no contamination rate is assumed in advance.

Criterion
τ_cost = C_FP / (C_FP + C_FN) p ≥ τ_cost → hold side; p < τ_cost → release side

C_FP = expected cost of one false release; C_FN = expected cost of one false hold; p = posterior probability of contamination.

Challenge pointWho prices the two costs, and how those prices are audited; where the costs come from the client contract, the threshold must be recomputed with the contract annex and entered in the version record.

MTH-02Operating constraint

Operating floor

Operational floor

The operating floor may only raise the interception probability; no model may lower it on its own.

Criterion
τ_hi = max(τ_cost, τ_min) τ_min = 0.15 // default

Any τ_min below the default must be listed in the contract annex and written into the decision record's method_version and the label metadata.

Challenge pointThe floor is a business constraint, not a statistical finding. A client may replace it, but it must be written into the contract; otherwise it may not be used for issuance.

MTH-03Evidence bands

Two-threshold triage

Two-threshold evidence

Above the high threshold, isolate immediately; above the low threshold, require microscopy review, so an uncertain sample is never released outright.

Criterion
τ_lo = max(0.06, 0.45 · τ_hi)
p bandActionRecord required

τ_lo ≤ p < τ_hiMicroscopy reviewReview conclusion written back; the case cannot be closed without it

Challenge point0.06 and 0.45 are engineering constants, not estimates from data; changing the crop or the cost of review requires re-validation.

MTH-04Hard gates

Hard-gate score cap

Hard-gate score cap

The weighted score only ranks above the gates; it cannot override a hard constraint.

Criterion
cap = 100 if N_root < 3: cap = min(cap, 55) if browning > 60%: cap = min(cap, 60) if p ≥ 0.5: cap = min(cap, 40) S_final = min(S_weighted, cap)
TriggerScore cap
Root count N_root < 3≤ 55
Browning browning > 60%≤ 60
Contamination posterior p ≥ 0.5≤ 40

Challenge pointThe three caps come from incident reviews. When several gates fire at once only the lowest cap applies; whether that is enough to cover cross-cutting risk has to be tested with counter-examples.

MTH-05Output semantics

Abstention semantics

Abstention semantics

Abstention is a formal output, not an error code. It must be written to the ledger and counted in the statistics, never padded with a default action.

Criterion
precedence: need_more_info ≻ abstain ≻ no_safe_option ≻ defer_to_human ≻ decision
OutputTriggerDownstream action
need_more_infoA field is missing or two fields conflictName the missing fields and a deadline
abstainInput outside the training distribution, or a confidence interval straddling the thresholdNo direction given; route to a human
no_safe_optionThe feasible set is emptyEmit this semantic; the process is set to stop_and_review
defer_to_humanA cost parameter is unconfirmed or beyond authoritySend to someone with the authority to sign

Challenge pointno_safe_option and defer_to_human boundaries are fixed by the decision tree; any change to that tree requires a release.

MTH-06Feasible set

Feasibility before utility

Feasibility before utility

Pass the hard constraints first, then compute utility, then rank only inside the feasible set. A high return may never compensate for a prohibited action.

Criterion
F = { a ∈ A | g_k(a) ≤ 0, ∀k = 1..K } if F = ∅ → no_safe_option + stop_and_review P(a) = exp(β · U(a)) / Σ exp(β · U(a')), a, a' ∈ F β = 6 a* = argmax P(a), a ∈ F

g_k is the hard-constraint function; U is the expected utility; β=6 is ranking sharpness and applies only inside the feasible set.

Challenge pointWhether the hard-constraint set K is complete, and whether β=6 needs recalibration when the cost scale changes.

MTH-07Evidence freezing

Hash-chain freezing

Hash-chain freeze

Decision and label share one structure: any change to a field must change the hash, and an old record can never be overwritten.

Criterion
h_i = fnv(prev_hash ‖ canonical(payload_i)) canonical: keys in lexicographic order · UTF-8 · no redundant whitespace · decimal numerals

The payload skeleton holds method_version、inputs_digest、output、decided_at; the label uses the same skeleton and can be recomputed independently.

Challenge pointFNV-1a-64 provides tamper detection only; it is not a collision-resistance commitment. External anchoring is the client's decision. A change to the canonicalisation implementation must ship as MAJOR and start a new chain.

MTH-09Data quality

Data-quality grading

Data-quality grade

The metered share sets the grade, and the grade sets the evidence price and the points coefficient. Estimated data cannot buy an A.

Criterion
q = metered_kWh / (metered_kWh + estimated_kWh) A: q ≥ 0.70 B: 0.45 ≤ q < 0.70 C: q < 0.45

The coefficients must be fixed in the contract annex and apply to new batches only; issued labels keep their original version.

Challenge pointWhether the denominator includes estimated energy, whether the metering window is cumulative or continuous, and how lost samples are counted — each choice changes the grade, so all three must be written into the rule snapshot.

MTH-10Batch boundary

Batch integrity

Batch integrity

The batch is the smallest unit of issuance, not a billable unit that can be split.

Criterion
valid_batch ⇔ |B| ≥ 240 ∧ (max t_harvest − min t_harvest) ≤ 24h ∧ harvest_windows(B) = 1

Same lineage within 24 h merges into one batch; one batch maps to one harvest window; splitting to farm issuance fees is prohibited.

Challenge pointThe 240-plantlet floor is an operating constraint, not a statistical optimum; the 24 h boundary must be a closed interval; and where the client does not share lineage the rule cannot be executed.

MTH-11Reduction baseline

Baseline co-signing

Baseline co-sign

The reduction baseline is frozen by both parties at contract signature; the platform may neither set it unilaterally nor adjust it retroactively.

Criterion
B0 = (yield_ref, energy_ref, EF_ref, boundary, period) reduction = (E_ref − E_actual) / E_ref valid_reduction ⇔ sig_client(B0) ∧ sig_platform(B0)

Without both signatures no reduction statement may be issued; a baseline may only be updated through a contract annex, never swapped silently at runtime.

Challenge pointWhether the co-signing party can actually verify the baseline, which reference year applies when history is missing, and whether baseline updates may only travel through the contract annex.

MTH-12Version governance

Versions cannot be edited retroactively

Non-retroactive versioning

A method change must ship a new version number; old labels point at the old version forever, and silent recomputation or overwrite is prohibited.

Criterion
version = CJV-MTH-{MAJOR}.{MINOR}[.{PATCH}] MAJOR = immutable item or semantic change MINOR = threshold / parameter change PATCH = editorial fix that changes no criterion

Old labels' method_version cannot be modified; a new version produces new labels and may never write back to an old record.

Challenge pointWhat counts as an editorial fix that changes no criterion needs a whitelist; otherwise PATCH becomes a way around the version record.
