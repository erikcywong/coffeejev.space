The label: fields, a specimen, the JSON structure, and how anyone verifies it

label schema · printed mock · signed record · public verification

The label has exactly one design goal: given the label id and hash, an outsider can recompute the same number without us. So no required field is decorative: drop one and the verification chain breaks.

The value is computed against the conventional soil-nursery baseline this method defines, 0.42 kgCO2e/plantlet (0.34–0.52). It is a relative difference, not an absolute environmental claim.
how to read it

Why every element is printed

  • The large 0.200 and its unit — the single claim; it competes with no other number
  • −52% vs baseline — it must carry the "vs baseline" qualifier; a bare −52% is a misstatement
  • The line-item bars — so a buyer sees at once that electricity dominates, and where the abatement lever is
  • The rounding line, listed separately — 0.0057 is hidden in no line item, so the parts sum to the declared value
  • PRIMARY 65.5% — disclosing the secondary share raises credibility rather than lowering it
  • VERIFICATION PENDING — the status prints PENDING until verification is complete; never a tick
  • The full hash — all 64 bits, not an abbreviation, so nobody has to argue about truncated-hash collisions
  • The footer disclaimer — states plainly that this is not a carbon credit; a compliance floor, not rhetoric

What the hash covers: every field except hash itself (including verification、factors、inputs_digest), canonicalised by JSON.stringify key order (lexicographic, no whitespace, no zero-padding) and then SHA-256. The canon must be published, or the same data yields different hashes.

4.4 Verification: from id and hash to a recomputation public verification

verifier path · anyone

Five steps, no account with us

  1. Scan or type the id → fetch the label record. The QR contains only label_id plus the first 12 hash digits, and no personal data.
  2. Recompute the hash → recompute SHA-256 over the record under the published canon and compare byte for byte with hash . A mismatch means the page or the record was edited.
  3. Recompute the emissions → multiply the record's activity × factors：134.4 × 0.425833 = 57.232, add line by line to 93.280, and check that ceil → 0.200. Any mismatch turns the page red.
  4. Check the chain → use prev_hash to walk back through batches to the genesis of the chain (offline; no bulk data needed). A broken link invalidates the label.
  5. Verify the raw data → request the raw interval series for inputs_digest and check it with the same digest algorithm. This step requires authorisation from the data holder (verifier, buyer due diligence, regulator); it is not fully public.
design rules

Four hard constraints

  • A hash cannot be written back: after closing, the record is read-only; a revision ships a new version (version+1) and keeps the old one
  • Digest granularity ≤ 60 s: raw intervals are kept for 24 months, then only the digest (the balance between storage and verifiability)
  • Factors are versioned：factors fully embedded in the record, never an external link — or it cannot be recomputed five years from now
  • No dependence on our domain: everything needed is in the record and the hash; the page is an entrance, not a precondition

Verification that requires logging into our platform is not verification; it is a display.
