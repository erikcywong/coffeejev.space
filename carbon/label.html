04 / CARBON LABEL

碳标签：字段、样张、JSON 结构，以及任何人如何验证它

label schema · printed mock · signed record · public verification

标签的设计目标只有一个：拿到标签 ID 和哈希，一个外部人可以不依赖我们，独立重算出同一个数。所以必需字段里没有任何一项是"装饰性"的——少一项，验证链就断。

4.1 必需字段 required fields

字段示例为什么必须有
label_idCJV-CN-YN-2026-000417对外唯一标识；解析规则 站-国-省-年-序号，可离线校验格式合法性
batch_idCJV-B-2026-0417回到批次账本；一个标签对应且仅对应一个封账批次
declared_unitplantlet功能单位枚举：plantlet / kg_green_bean。否则 0.200 是在说什么都不知道
kgco2e_per_unit0.200声明值本身，向上取整后的口径
breakdown{electricity:0.1192, …}分项可加性校验：外部人能求和、能定位差异
boundarycradle-to-gate边界不同不可比；必须与 §2.2 清单同版本
gwp_versionIPCC AR6 · GWP100AR5/AR6 结果不可直接比；不写版本等于不可比
data_quality_gradeA决定积分乘数（1.0/0.9/0.8），也是买方可信的代理指标
verification{status, body, date}核证状态必须显式：self / third_party。未核证不得印 VERIFIED

prev_hashsha256:5c71…2938形成批次链；删除或改写任一批次都会断链

how to read it

样张上每一处印刷的用意

  • 大字 0.200 + 单位 — 唯一主张，不与任何别的数字争版面
  • −52% vs baseline — 必须带 "vs baseline" 限定词，单独一个 −52% 属不实表述
  • 分项条 — 让买方一眼看出"电是大头"，从而知道减碳杠杆在哪
  • 取整项单列 — 不把 0.0057 藏进任何分项，保证分项之和 = 声明值
  • PRIMARY 65.5% — 主动披露二次数据占比，反而提升可信度
  • VERIFICATION PENDING — 核证未完成时印 PENDING，绝不打勾
  • 完整哈希 — 印全 64 位而非缩略，避免"缩略哈希碰撞"的质疑
  • 底部免责 — 明确非碳信用；这是合规底线，不是修辞

hash 的覆盖范围：除 hash 字段自身外全部字段（含 verification、factors、inputs_digest），按 JSON.stringify 的键序规范化（字典序、无空白、数字不补零）后取 SHA-256。规范化算法必须公开，否则同一份数据会算出不同哈希。

4.4 验证流程：从 ID + 哈希到重算 public verification

verifier path · 任何人

五步，不需要我们的账号

  1. 扫码或输入 ID → 拿到标签记录。QR 内容只含 label_id + 哈希前 12 位，不含任何个人信息。
  2. 重算哈希 → 按公开的规范化规则对记录重算 SHA-256，与 hash 逐字节比对。不一致 = 页面或记录被改过。
  3. 重算排放 → 用记录里的 activity × factors：134.4 × 0.425833 = 57.232，再逐项求和得 93.280，ceil → 0.200。任一步不符即在页面标红。
  4. 校验链 → 用 prev_hash 回溯上一批次，直到链首（可离线校验，不需要全量数据）。断链即失效。
  5. 验证原始数据 → 请求 inputs_digest 对应的原始区间序列，用同一摘要算法核对。这一步需要数据方授权（核证方、买方尽调、监管），不是全公开。
design rules

四条硬约束

  • 哈希不可写回：封账后记录只读，修订必须出新版本（version+1）并保留旧版
  • 摘要粒度 ≤ 60 s：原始区间保留 24 个月，之后只保留摘要（存储与可验证性的平衡）
  • 因子版本化：factors 全部内嵌在记录里，不引用外部链接——否则五年后无法复算
  • 不依赖我们的域名：验证所需的一切都在记录与哈希里；页面只是入口，不是验证的前提

若把验证做成"必须登录我们的平台才能看"，那它就不是验证，是展示。
